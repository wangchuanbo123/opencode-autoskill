# AutoSkill evaluation

`npm run evaluate` uses only the bundled synthetic corpora. It does not call a model, read credentials, or inspect real user sessions. Candidate validation, complexity prescreen, and skill-retrieval routing results are reported separately. None establishes semantic truthfulness, useful skill synthesis, confidence calibration, or future reuse outcomes.

## Reuse retrieval routing

`reuse.json` contains a compact catalog of synthetic generated skills and 11 separately labeled task scenarios. The labels distinguish expected candidates, prohibited candidates, and skills expected to qualify for automatic context loading. Scenarios cover concrete English/Chinese triggers, generic or unrelated tasks, application-framework and runtime-version conflicts, unknown versus observed prerequisites, and current-user opt-outs.

The `reuse` report includes `scenarioAccuracy`, `candidateRecall` for explicitly required candidates, `falseAutoLoads`, `missedAutoLoads`, `autoLoadPrecision`, `autoLoadRecall`, and per-case scores/reason codes. It compares local routing with these labels. An automatic load means the policy selected content to provide to the main model, not that the model used it, executed its steps correctly, or caused task success. Do not report any of these values as the real skill reuse success rate.

Replay uses a fixed synthetic date so stale-version handling does not change as the calendar advances. No actual project files, local credentials or runtime are inspected. The retrieval unit suite separately covers hundreds of irrelevant candidates, bounded output, duplicate/conflicting methods, hashes, manual changes, pinning, expiration, sensitive content, negative feedback, multiple runtime requirements and platform constraints.

`--responses` and `--endpoint` apply only to candidate-review decisions. Reuse routing remains local and makes no additional endpoint requests in either mode. The process exits unsuccessfully if any candidate gate, prescreen label, or reuse routing label fails.

## Complexity prescreen replay

`complexity.json` labels whether observed execution evidence merits a semantic review. Its 13 scenarios include repeated same-file reads, ordinary multi-file inventory, spelling corrections, unchanged-command retries, concrete two-call diagnosis, diagnosis followed by a changed method, coordinated producer/consumer migration, read-only reconciliation, missing verification, routine bulk edits, repeated Code Mode reads, Code Mode data dependencies, and unfinished execution.

The `prescreen` report includes accuracy, false accepts, false rejects, precision, recall, each human label's rationale, and the implementation's dimensions/reason codes. “Accept” means send the evidence for further assessment. It does not mean publish a Skill. The default call-count settings and legacy values of `1` must both reject routine examples; changing the old thresholds cannot bypass substantive criteria.

These are small hand-labeled synthetic examples, intended to catch rule regressions and the old call-count shortcut. The labels were written as task-level expectations, not generated by copying the scorer's formulas. A passing corpus is not a representative population benchmark. Real tasks should be independently labeled and reviewed before claiming general precision or recall.

The same limitation applies to retrieval labels: lexical scoring, aliases and known-constraint parsing are fallible. Representative multilingual tasks, dense overlapping skill collections and independently reviewed actual usage are needed before making claims about general retrieval quality or useful automation.

## Candidate and reviewer replay

The reported `gateAccuracy` measures deterministic candidate acceptance/rejection rules.

The corpus includes labeled candidate outputs and observed tool evidence. To replay outputs collected from an actual reviewer:

```powershell
npm run evaluate -- --responses D:\evaluation\responses.json
```

The JSON object must contain every `kind: "decision"` case ID in `corpus.json`, with each value being the reviewer decision object. Unknown IDs and missing decision cases are errors. Replay does not silently fill gaps with bundled outputs. Task privacy cases continue to use their deterministic fixture. Prefer adding more representative labeled cases before interpreting the result as broad model quality.

The default `candidate-gates` mode evaluates the bundled candidate against its `expected` gate label. Reviewer replay/endpoint modes use `reviewExpected`, which labels whether that evidence should lead to publication. An accepted `skip` decision counts as no publication. In particular, the bundled prompt-injection candidate must be rejected by the gate, while a real reviewer seeing its valid evidence may safely produce a clean skill. Reviewer modes report `fixtureDecisionAccuracy`; this is an outcome label check on the small synthetic fixture, not a claim of semantic quality.

An explicit generic reviewer endpoint can be used for a paid or local model:

```powershell
$env:AUTOSKILL_EVAL_TOKEN = "your-endpoint-token"
npm run evaluate -- --endpoint http://127.0.0.1:9000/review
```

The script sends `POST` JSON `{ "id": "case-id", "prompt": "...", "evidence": [...] }` with `Authorization: Bearer $AUTOSKILL_EVAL_TOKEN`. The prompt is produced by the same `buildReviewInput` code used by the plugin. The server must return a decision object directly, or `{ "output": <decision object> }`. This is a generic adapter contract, not an OpenAI-compatible chat endpoint. Connect a provider through a small adapter which executes the supplied prompt and returns parsed JSON. Each request has a 30-second timeout. Transport errors, non-2xx responses, and invalid response JSON are evaluation failures; they cannot satisfy an expected reject label.

`--endpoint` and `--responses` are mutually exclusive. Endpoint mode makes a request for every decision case. Credentials are read only from the explicitly named environment variable, never from OpenCode or user credential stores. The local HTTP stub test covers endpoint use without contacting a paid provider.
